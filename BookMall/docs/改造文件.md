你这个判断其实是对的。

图片里的这些项目**不是“不行”**，甚至从技术栈上看已经覆盖了 MCP、RAG、Agent、Spring AI、知识库、工作流、智能客服这些现在比较主流的东西。问题在于：

> **它们更像“AI 技术能力展示项目”，而不是“企业业务系统”。**

这两者在面试里的杀伤力完全不一样。

我刚看了一下现在企业 Agent 的落地方向，企业真正关心的已经不是“我能不能让 LLM 调一个 MCP Tool”，而是**权限、业务规则、流程状态、异常恢复、人工审批、审计、可观测性、成本和可靠性**这些东西。腾讯云、阿里云现在的企业 Agent 架构也都明显往“Agent + Workflow + 企业知识 + 业务系统工具”这个方向走。([腾讯云开发者平台][1])

所以如果你要做一个**秋招拿来狠狠干面试官的项目**，我反而不建议你再做：

> ❌ AI 智能客服
> ❌ AI 知识库
> ❌ MCP 工具箱
> ❌ 多 Agent 对话
> ❌ 一站式 AI 平台

这些已经太容易撞车了。

---

# 我更建议你做一个：

# **企业级 AI 售后工单与异常处置平台**

可以把它理解成：

> **“淘宝/京东/跨境电商背后的 AI 售后运营系统”**

不是做一个聊天框。

而是做：

```text
用户投诉/订单异常
        ↓
     AI 接入层
        ↓
   意图识别 + 风险判断
        ↓
     工单中心
        ↓
 ┌──────┼────────┐
 ↓      ↓        ↓
订单系统 物流系统   商品/库存系统
 ↓      ↓        ↓
支付系统  售后系统   企业知识库
        ↓
   AI Agent 决策
        ↓
   Workflow 编排
        ↓
 ┌──────┼─────────┐
 ↓      ↓         ↓
自动处理  人工审批   转人工
        ↓
      执行
        ↓
   审计 + Trace
```

这就开始有点**企业系统的味道**了。

而且这不是我为了凑项目硬编的方向。现在企业 Agent 实际落地就大量集中在客服、售后、订单、物流、内部助手等场景，例如腾讯云 ADP 的案例里就有订单查询、物流跟进、售后服务、理赔助手等。([腾讯云 ADP][2])

# 一、为什么这个项目比图片里的项目更适合你

图片里的：

> “实践 MCP，让 LLM 拥有超能力”

面试官很容易问：

**“你的 MCP Server 做了什么？”**

然后你：

> “可以查询天气、数据库、调用业务接口……”

面试官：

> “为什么不用普通 HTTP？”

结束。

甚至：

> “你这个 Agent 为什么一定要 Agent？”

又结束。

因为**技术没有被业务约束**。

---

而我们的项目可以反过来。

你先定义业务：

> 一个电商平台每天产生大量售后工单。

例如：

```text
订单 10086

用户：
“我买的手机已经显示签收了，但是我没收到。”

系统：
创建售后工单

AI：
1. 查询订单
2. 查询物流
3. 查询签收位置
4. 判断是否存在异常
5. 查询历史相似工单
6. 判断赔付规则
7. 给出处置方案

如果赔付金额 < 50：
    自动赔付

如果 50 <= 金额 < 500：
    AI 给方案
    → 人工审批

如果金额 >= 500：
    强制人工

如果检测到欺诈风险：
    → 风控系统
```

这时候 MCP、RAG、Agent、Workflow 全都有了。

但是它们已经不是项目的主角。

**业务才是主角。**

这就完全不一样了。

# 二、真正让这个项目“亮”的，是领域知识

你刚才说：

> “我感觉加一点领域知识能做。”

这个判断非常关键。

甚至我建议你把项目设计成：

> **70% 后端业务系统 + 30% AI**

而不是：

> 20% 后端 + 80% AI Prompt。

这是你现在最应该避免的坑。

---

# 三、领域知识可以怎么加？

比如我们定义一个**电商售后领域模型**。

至少有：

```text
Order
订单

OrderItem
订单商品

AfterSale
售后单

Ticket
客服工单

Refund
退款单

Logistics
物流单

Compensation
赔付单

RiskRecord
风险记录

WorkflowInstance
工作流实例

Approval
审批记录
```

然后定义状态机。

比如售后：

```text
CREATED
   ↓
UNDER_REVIEW
   ↓
WAITING_USER
   ↓
WAITING_APPROVAL
   ↓
PROCESSING
   ↓
COMPLETED
```

但真正有意思的是：

**状态不能随便跳。**

例如：

```text
CREATED → COMPLETED
```

不允许。

必须：

```text
CREATED
  ↓
UNDER_REVIEW
  ↓
PROCESSING
  ↓
COMPLETED
```

如果 AI：

```json
{
  "action": "REFUND",
  "amount": 800
}
```

也不能直接执行。

必须经过：

```text
AI Decision
     ↓
Business Rule Engine
     ↓
Risk Check
     ↓
Permission Check
     ↓
Approval Policy
     ↓
Refund Service
```

这一下，项目的**后端味道就出来了**。

---

# 四、AI 在这里到底干什么？

AI 不负责“当数据库”。

AI 负责：

> **理解 + 判断 + 规划**

确定性系统负责：

> **执行 + 一致性 + 权限 + 状态**

这是一个特别重要的架构思想。

比如用户说：

> “东西没收到，但是物流显示签收了，我也懒得折腾了，直接给我退款吧。”

LLM 判断：

```text
Intent:
物流异常 + 退款申请

Entities:
order_id = 10086

Risk:
medium

Suggested Action:
查询物流
```

然后 Agent 调：

```text
query_order()
query_logistics()
query_delivery_proof()
query_user_history()
```

拿到：

```text
订单：手机 ¥3999
物流：已签收
签收位置：小区驿站
用户历史：第一次投诉
风险评分：低
```

AI 再判断：

```text
建议：
联系用户确认驿站
暂不退款
```

如果用户确认：

```text
“驿站没有，我确定没收到”
```

Agent 再进入下一步。

# 五、这里就可以出现非常漂亮的 Workflow

例如：

```text
              售后工单
                  │
                  ▼
             意图识别
                  │
          ┌───────┴───────┐
          ↓               ↓
       咨询类           售后类
                          │
                          ▼
                     查询订单
                          │
                          ▼
                     查询物流
                          │
                          ▼
                      风险评估
                          │
              ┌───────────┼───────────┐
              ↓           ↓           ↓
             低风险      中风险       高风险
              ↓           ↓           ↓
            自动处理    人工审批     风控介入
              │           │           │
              └───────────┴───────────┘
                          ↓
                      执行售后
                          ↓
                     工单关闭
```

而且这个 Workflow **不是为了炫技术写出来的**。

它是业务要求：

> 不同风险等级必须走不同流程。

这就非常适合面试。

# 六、然后你可以把 MCP 真正用起来

这里 MCP 就不是：

```text
get_weather()
search_google()
calculator()
```

这种玩具工具。

而是：

```text
Order MCP Server
├── query_order
├── query_order_items
└── check_order_status

Logistics MCP Server
├── query_logistics
├── query_delivery_proof
└── query_logistics_exception

├── query_after_sale
└── apply_refund

Risk MCP Server
├── check_user_risk
├── check_fraud

```

然后：

```text
AI Agent
    │
    ├── Order MCP
    ├── Logistics MCP
    ├── AfterSale MCP
    └── Risk MCP
```

这时候你面试的时候就能说：

> **“我没有让 Agent 直接访问数据库，而是通过领域工具暴露受控业务能力。”**

这句话就比：

> “我做了一个 MCP Server。”

高级很多。

# 七、再往后，你甚至可以做“AI 决策”和“业务执行”的隔离

这个非常适合你。

例如：

```text
LLM
 ↓
Decision
 ↓
{
   action: "REFUND",
   amount: 3999,
   reason: "物流异常"
}
 ↓
Policy Engine
 ↓
是否允许？
 ↓
Risk Engine
 ↓
是否需要审批？
 ↓
Workflow
 ↓
Refund Service
```

这里有一个很重要的原则：

> **LLM 可以提出决策，但不能拥有最终业务权限。**

这就是企业 AI 和 Demo AI 的区别之一。

# 八、然后你可以疯狂塞后端面试题

这才是我真正觉得这个项目适合你的原因。

例如：

### ① 幂等

用户连续说：

> “给我退款。”

Agent 调了两次：

```text
refund()
refund()
```

怎么办？

```text
idempotency_key
```

例如：

```text
order_id + after_sale_id + action
```

保证退款不会执行两次。

---

### ② 分布式一致性

退款成功了。

但是：

```text
工单状态更新失败
```

怎么办？

你就可以讨论：

```text
Outbox
+
MQ
+
Retry
+
Idempotent Consumer
```

---

### ③ Agent 调工具超时

```text
query_logistics()
```

超时怎么办？

```text
timeout
retry
circuit breaker
fallback
```

---

### ④ Workflow 执行到一半挂了

例如：

```text
Step1 查询订单     ✓
Step2 查询物流     ✓
Step3 风险检查     ✓
Step4 退款         ✓
Step5 更新工单     💥
```

服务重启以后怎么办？

你就可以设计：

```text
WorkflowInstance
WorkflowStep
StepStatus
RetryCount
Checkpoint
```

恢复执行。

这时候就已经非常像真正的企业工作流系统了。

# 九、再加一个非常关键的东西：人工审批

这个特别重要。

因为真实企业不可能让：

> “LLM 觉得应该赔 5000 元”

然后服务器：

> “好的主人。”

直接打钱。

人类终于在系统里发挥了一点作用。

设计：

```text
AI Decision
     ↓
Policy Engine
     ↓
需要人工审批
     ↓
Approval Task
     ↓
人工：
    approve / reject
     ↓
Workflow Resume
```

甚至可以：

```text
AI 推荐：

退款 ¥3999
理由：
物流异常 + 用户历史低风险
证据：
订单、物流、用户历史

[批准] [拒绝]
```

这个项目一下就出现了：

* Agent
* RAG
* MCP
* Workflow
* Human-in-the-loop
* RBAC
* Audit
* State Machine
* MQ
* Redis
* MySQL
* Distributed Idempotency

但它们不是硬塞进去的。

**每个技术都有业务理由。**

# 十、再做一个 RAG，但别做“上传 PDF 问问题”

这个已经烂大街了。

你做：

# 售后规则知识库

例如：

```text
《七天无理由退货规则》
《手机类商品售后规则》
《物流丢件赔付规则》
《生鲜商品赔付规则》
《会员赔付规则》
《高风险用户赔付规则》
```

然后 AI 要回答：

> “这个订单为什么不能直接退款？”

不仅返回：

```text
不能退款
```

而是：

```text
根据《手机类商品售后规则》第 3.2 条：

已激活设备不支持无理由退货。

当前订单状态：
设备已激活

因此：
不能走普通退款流程。
```

这才是企业知识库。

# 十一、甚至可以进一步做“规则版本化”

这个非常适合面试。

例如：

```text
2026-08-01
退款金额 <= 100
自动审批

2026-09-01
退款金额 <= 50
自动审批
```

那么：

> **一个 8 月创建的工单，到底应该按照哪个规则？**

你不能简单地：

```sql
SELECT current_rule
```

而应该考虑：

```text
Policy Version
+
Effective Time
```

比如：

```text
Policy v12
effective_at = 2026-08-01
```

工单创建时绑定：

```text
policy_version = 12
```

这就是非常典型的企业业务问题。

# 十三、这个项目和图片里的项目，最大的区别

我给你一个非常直观的对比：

| 普通课程项目       | 你应该做的项目          |
| ------------ | ---------------- |
| MCP 工具箱      | 业务领域 MCP         |
| AI 客服        | 售后工单系统           |
| RAG 知识库      | 售后规则知识库          |
| Agent        | 售后决策 Agent       |
| Workflow     | 售后状态机 + Workflow |
| Tool Calling | 受控业务操作           |
| Chat         | 工单生命周期           |
| Prompt       | 业务决策             |
| MySQL        | 领域数据模型           |
| Redis        | 幂等/缓存/分布式状态      |
| MQ           | 异步业务事件           |
| 日志           | 审计 + Trace       |
| Demo         | 企业业务系统           |

所以我会给你一个非常明确的判断：

> **你现在不缺“AI 项目”。**
>
> 你缺的是一个能够把你已经学的 AI 技术，全部压到一个真实业务领域里的项目。

# 十四、而且这个项目特别适合你的求职定位

你现在是：

> **Go 后端 + AI 应用开发**

那最好的项目不是：

> “我是一个 AI Agent 开发者。”

而是：

> **“我是一个懂后端工程，又能把 LLM/Agent 放进真实业务系统里的开发者。”**

这两个定位在面试的时候差距很大。

因为前者很容易被问：

> Prompt 怎么写？

后者可以被问：

> 为什么用 MQ？

> 为什么不用 Redis Stream？

> Agent 崩溃怎么办？

> Workflow 如何恢复？

> 怎么保证退款幂等？

> Tool 调用失败怎么办？

> 为什么 AI 不能直接调用 Service？

> 如何防止重复退款？

> 如何实现人工审批？

> RAG 如何评估？

> 知识库更新如何保证最终一致？

> 规则变化后历史工单怎么办？

> 10 万工单并发怎么办？

这些才是你真正应该拿来准备秋招的东西。

## 最后，我甚至建议你别急着写代码

先把项目设计成 **“企业真的会买的东西”**。

我建议最终项目名直接叫：

> ### **AI 售后智能运营平台**
>
> **Enterprise AI After-Sales Operations Platform**

核心不是“AI 客服”，而是：

```text
订单异常
   ↓
AI 分析
   ↓
工单
   ↓
业务规则
   ↓
Agent 决策
   ↓
Workflow
   ↓
自动执行 / 人工审批
   ↓
结果
   ↓
审计 / 监控 / 评估
```

然后我们再从**业务领域建模**开始，一层一层把它设计出来：

**业务流程 → 领域模型 → 数据库 → 状态机 → API → MQ → 幂等 → Workflow → Agent → MCP → RAG → 权限 → 可观测性 → 压测 → 面试题。**

这样做出来的东西，才不是“又一个 AI 项目”。

而是一个**披着 AI 外衣、骨子里是真正后端企业系统**的项目。

这条路线其实非常适合你现在的阶段。你已经接触过 Redis、MQ、RAG、Agent、Go 后端、分布式这些东西，现在最缺的不是继续横向加技术名词，而是把这些东西**压缩到一个足够真实的业务问题里，形成系统性能力**。这一步比再刷十个课程项目值钱得多。([architect.salesforce.com][3])
