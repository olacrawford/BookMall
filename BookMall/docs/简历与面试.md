# 秋招简历与面试准备

## 唯一目标

整个项目的一切工作最终只服务一件事：

> 秋招简历上写得出差异点，面试现场讲得清落地过程。

因此每个阶段结束都必须回答两个问题：

1. 这一阶段能不能给我简历增加一个可写点？
2. 面试官追问这个点，我能不能讲出“业务问题、方案取舍、失败处理”？

不能写进简历或不能支撑面试追问的功能，优先级自动下降。

## 面试讲解顺序

1. 先讲业务问题：电商售后为什么不能只有一个聊天框
2. 再讲总体架构：AI 决策域、售后业务域、交易域
3. 挑一条完整链路：用户投诉 -> AI 分析 -> 规则 -> 审批 -> 退款 -> 审计
4. 主动讲一个失败场景：消息重复、流程中断、模型输出不合法
5. 最后给增强方向：真实 LLM、向量库、评测、可观测性

主动先讲失败场景比被追问好，因为能证明不是“Demo”。

## 高频面试题与最短答案

### 项目类

1. 为什么不做 AI 智能客服？

   AI 客服问题在于没有业务状态、审批、退款、审计；本项目把问题放进工单和流程中解决。

2. AI 在这里到底做了什么？

   理解用户诉求、抽取实体、收集证据、召回规则、给出建议；不负责最终执行。

3. 为什么需要 Agent？

   一个接口解决不了多工具、多证据、多步骤判断；Agent 把“查订单、查物流、查规则、判断风险”串起来。

4. 为什么必须用 MCP？

   MCP 不是必须，真正价值是统一工具接入和受控能力；普通 HTTP 没有明确工具契约，MCP 提供标准化边界。面试时可说“重点是工具白名单和执行边界”。

### 状态机与业务规则

5. 状态机怎么防止非法跳转？

   定义合法迁移表，每次变更校验 `currentStatus + event -> nextStatus`，不合法直接抛业务异常，并写单测覆盖。

6. 为什么规则要有版本？

   规则会变，历史工单应该按创建时规则处理，否则结果不稳定、无法解释、无法审计。

7. 自动退款和人工审批怎么决定？

   用 `PolicyService` 按退款金额、风险等级、商品类目、售后类型综合判断。

### 可靠性与一致性

8. 退款怎么防止重复？

   使用 `refund_no / order_id / action / amount` 等业务幂等键，数据库加唯一约束，执行前检查退款状态。

9. 消息重复消费怎么处理？

   消费者根据业务幂等键或当前状态判断；已处理直接返回成功，不重复执行。

10. 退款成功但更新订单失败怎么办？

   退款记录先落库，通过 Outbox/MQ 异步通知订单；消费端幂等重试，最终一致。

11. 为什么用 Outbox？

   本地事务成功后，同一事务写待发事件，由 Worker 发送；避免“业务成功但消息没发出”。

12. 流程执行一半宕机怎么恢复？

   每个 WorkflowStep 落库，保存状态、重试次数、下一次执行时间；恢复扫描重跑未完成步骤。

### RAG 与模型

13. 为什么不能直接让模型回答售后规则？

   模型没有你的规则版本，还容易记错；RAG 先召回规则，再让模型依据条款回答，并返回来源。

14. 第一周没有向量库怎么做 RAG？

   先把规则分块存 MySQL，按关键词、标签、类目召回；效果够演示，后续换向量库。

15. 怎么评估 RAG？

   准备种子问题，看是否召回正确规则、版本是否对应、回答是否引用正确条款；记录正确率。

16. 没有大模型 Key 怎么跑？

   `LlmClient` 内置 Mock 实现，按契约返回决策；真实 Provider 只替换实现。

### 架构类

17. 为什么还要保留原来订单/支付/库存？

   售后必须建立在真实交易状态上，否则没有退款目标、没有金额、没有库存联动。

18. 为什么不拆更多微服务？

   按领域边界拆：交易域、售后域、AI 域；第一周避免过度拆分，重点是把边界设计清楚。

19. 怎么防止用户越权？

   网关透传可信的 `X-User-Id`，售后接口校验 `ticket.userId`；运营接口按角色权限控制。

20. 项目和课程 CRUD 区别在哪？

   有状态机、多实体流转、审批、幂等、消息、恢复、审计，不是单表增删改查。
