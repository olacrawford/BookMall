# AI 学习地图

这份文档只解决一个问题：为了把本项目走通、讲清、写进简历，AI 相关概念需要理解到什么程度。

核心态度是：

> 不要求看论文、不要求训练模型、不要求研究底层算法。要求能知道每个概念解决什么问题、在项目里放在哪里、输入输出是什么。

## 本周先理解这些概念

按阅读顺序学习，不要一次全背。

### 1. LLM 大模型

理解程度：

- LLM 是能根据输入文本生成回答/结构文本的程序
- 它没有数据库、不知道实时订单、也不知道你的售后规则
- 它可能“一本正经地胡说”，所以必须限制输出结构并附证据

本项目位置：

`bookmall-ai` 中的 `LlmClient`。第一周用 Mock，后续换真实模型。

不用学：

- 注意力机制
- Transformer 源码
- 训练/微调

### 2. Prompt 与结构化输出

理解程度：

- Prompt 是给模型的指令和上下文
- 生产项目尽量不依赖“碰运气”，要求模型输出固定 JSON，如 `{action, amount, reason, evidenceIds}`
- 系统需要对 JSON 做校验，解析失败就重试或标记失败，不能直接进入业务执行

本项目位置：

AI 分析工单时，输入 `TicketContext`，输出 `Decision`。

不用学：

- Prompt 工程高级技巧可以先不研究
- 不用追求“万能 Prompt”

### 3. Tool Calling

理解程度：

- 模型本身不能查订单、查物流
- 可以让模型输出“我想调用哪个工具以及参数”
- 系统负责真正执行工具，并把结果返回给模型

本项目位置：

Agent 调用订单查询、物流查询、规则检索等工具。

关键判断：

- 工具名和参数必须白名单化
- 退款/改状态不能作为 Agent 可调用工具

### 4. Agent 循环

理解程度：

- Agent 不是单一接口，而是一个循环：

```text
用户目标
  -> 模型想下一步
  -> 调用工具
  -> 把工具结果还给模型
  -> 继续想下一步
  -> 直到给出最终决策
```

- 真实项目必须有最大轮数、超时、失败退出边界

本项目位置：

第一周可以简化为“一次分析 + N 个并行证据查询 + 一次生成决策”，不追求复杂多轮。

### 5. MCP

理解程度：

- MCP 是一种“模型工具接入协议/标准插头”
- 核心不是协议本身，而是“统一暴露受控业务能力”
- 本项目重点是：工具清单、入参出参、鉴权、限流、调用审计

本项目位置：

`bookmall-mcp` 暴露订单/物流/售后/风控领域工具。

不用学：

- MCP SDK 细节第一周可以后补
- 只需能解释“MCP 解决的是标准化工具接入问题”

### 6. RAG

理解程度：

- RAG 是“先查资料，再让模型回答”
- 核心链路：文档 -> 分块 -> 入库/索引 -> 检索 -> 拼进 Prompt -> 模型回答 -> 标注来源
- 它的价值不是“更像搜索”，而是“让答案有证据、规则可溯源”

本项目位置：

售后规则知识库，例如《七天无理由退货规则》《手机类售后规则》。

第一周可用 MySQL 分块 + 关键词/标签检索，后续可换向量库。

不用学：

- Embedding 底层数学
- 向量检索索引算法底层

### 7. Embedding 与向量库

理解程度：

- Embedding 把文本变成一串数字，语义相近的数字更接近
- 向量库负责按语义相似度检索
- 这不是必须的，第一周用 MySQL 已经能跑通，一个月后再接

本项目位置：

后续 `rag_chunk.embedding` 和 vector db。

不用学：

- 向量距离公式可以只记名字和用途
- 不用实现向量索引

### 8. Evaluation 评测

理解程度：

- AI 项目要回答“你的 RAG 到底行不行”
- 简单做法：准备 20-30 个种子问题，看是否检索到正确规则、模型是否引用正确版本
- 用种子问题和评分表记录，不要只靠肉眼觉得“看起来不错”

本项目位置：

`t_rag_benchmark_case` 和 Stage 07 评测报告。

### 9. Human In The Loop 人机协同

理解程度：

- AI 可以建议，但关键操作必须有人确认
- 审批不是可选项，是业务对风险的控制
- 系统要有审批任务、审批人、通过/驳回、审批记录

本项目位置：

`approval_task`、Policy 判定、审批后继续 Workflow。

### 10. 失败与一致性

理解程度：

面试官区分 Demo 和系统，主要看失败场景：

- 退款重复执行怎么办 -> 幂等
- 消息丢失怎么办 -> Outbox/MQ 重试
- 流程执行一半宕机怎么办 -> 流程步骤落库 + 恢复
- 看不到调用链怎么办 -> audit + trace

本项目位置：

Stage 05 可靠性阶段。

## 后端概念同步理解

这些不是 AI 专属，但本项目必须会讲：

| 概念 | 一句话理解 | 本项目位置 |
| --- | --- | --- |
| 状态机 | 规定状态只能按合法路径迁移 | `AfterSaleStatusMachine` |
| 策略引擎 | 根据规则判断该自动/审批/风控 | `PolicyService` |
| 工作流 | 按固定步骤执行，每步可落库恢复 | `WorkflowInstance/Step` |
| 幂等 | 同一个请求重复执行，结果一致 | 退款、审批、消息消费 |
| Outbox | 事务里先写“待发送消息”，再异步发送 | `t_after_sale_outbox` |
| 消息队列 | 服务间通过事件解耦 | RabbitMQ |
| 审计 | 谁在什么时候做了什么，不可删除 | `t_audit_log` |
| Trace | 用同一个 trace_id 串联整条调用链 | 网关/服务日志/DB 审计 |

## 学习节奏建议

- 每天开始前花 15-30 分钟读对应概念，不深挖
- 每个概念写一句“放在我项目里是做什么的”
- 每完成一个阶段，用“面试官会怎么问”检验理解
- 不能只看概念，必须在代码或演示里找到对应位置

## 不学清单

- 不调模型，不训练模型
- 不研究 Attention、Tokenizer、梯度下降
- 不实现 RAG 算法，只使用组件
- 不研究 MCP 协议底层
- 不一开始就学 LangChain / Spring AI 全部 API
- 不先背面试题，先跑闭环再背
