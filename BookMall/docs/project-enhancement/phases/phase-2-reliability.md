# 阶段 2：处理重复、超时和越权（第 4 天）

## 目标与业务价值

让失败、重试、并发和越权成为可复现的系统行为，而不是演示时避开的偶然情况。

这一阶段直接对应简历里的“分布式长链路最终一致性”：重点不是把某个按钮做出来，而是证明跨服务、异步消息和长流程在抖动时仍能收敛到正确状态。

## 前置条件

阶段 1 两条确定性路径可跑；RabbitMQ 和 Redis 可用。

## 今天照着做

1. 在同一事务中插入退款结果和 `t_after_sale_outbox`，用日志打印 `event_id`。
2. 写一个测试把同一 `REFUND_EXECUTED` 消息投递两次，断言消费表或订单状态只变化一次。
3. 给物流查询 adapter 设置短超时，注入一次超时，确认工单转 `WAITING_HUMAN` 而不是退款。
4. 停掉 Worker，再启动恢复扫描，记录 `workflow_step` 的重试次数和终态。
5. 用普通用户 JWT 调审批接口、用用户 A 调用户 B 的详情接口，保存 403/业务拒绝证据。

## 修改范围

Outbox/Worker、消费幂等、超时重试、限流降级、角色校验、trace 过滤器和故障测试。

## 实施切片

1. 业务事务内写 Outbox；Worker 按 `next_retry_time` 发送并记录重试。
2. 消费端以 `event_id`/业务键幂等，重复消息直接 ack。
3. 工具和 Feign adapter 设置超时、有限重试和转人工降级。
4. 审批接口做角色 + 任务归属 + 状态条件更新。
5. Gateway 生成 `trace_id`，服务日志和审计共享。
6. 注入退款超时、消息重复、Worker 中断、非法 Decision 四类故障。

## 交付产物

可靠性测试、Outbox 状态样例、故障演练记录、权限测试和告警字段表。

## 验证方案

每个故障都记录注入动作、预期、实际状态、恢复时间和证据 ID；不写无数据的“高可用”。

## 风险与回滚

Outbox Worker 可开关；异常积压时暂停发送并人工重放。权限错误优先关闭运营写接口。

## 停止条件

重复退款或越权用例失败时，冻结前端展示，不继续扩展 AI。

## 面试证据

一次重复消息重放和一次流程中断恢复的完整日志链。

## 必须沉淀

- `THOUGHT.md`：说明为什么采用至少一次投递 + 幂等消费，哪些场景只做最终一致。
- `PIKE.md`：记录一个故障注入的 Problem、重试/降级决策和实际恢复证据。
- `CHANGELOG.md`：记录 Outbox 字段、Worker 开关、超时和权限变更。
- 面试卡片：退款成功但通知失败、重复消费、审批并发、普通用户越权四个故障推演。
