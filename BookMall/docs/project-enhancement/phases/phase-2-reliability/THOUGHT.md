# THOUGHT

阶段 2 最重要的理解不是“加一个队列”，而是把“投递”和“副作用”分开：消息可能重复，消费必须幂等。

今天有三个关键判断：

1. 退款结果和 Outbox 事件必须在同一本地事务写入。否则会出现退款已落库但事件没有产生，或事件先发出但退款回滚的窗口。
2. 工作流恢复不能直接把失败步骤改回原状态，而是走 `FAILED -> RETRYING -> COMPLETED`。这样能看到重试次数、错误码、下次重试时间，也能在审计里解释中断后的恢复过程。
3. 权限不能只靠前端隐藏入口。售后单详情、退款、审批都要在服务层校验 `X-User-Id`，Gateway 只负责注入可信身份，不负责替代业务权限。

继续补齐时又形成两个判断：

4. 物流查询必须是可替换的边界，而不是散落在业务代码里的硬编码成功。用 `LogisticsQueryGateway` 隔离外部依赖，再用 `mode=timeout/unavailable` 做故障注入，才能证明“查询失败不会自动退款，而是进入 `WAITING_HUMAN`”。
5. 数据库 Outbox 扫描是恢复通道，不是替代真实消息中间件。正常路径由 RabbitTemplate 发布退款事件，发布成功后再把事件置为 `DISPATCHED`；发布失败时事务回滚，事件留在 `CREATED`。扫描调度负责补发，而不是把所有消息都推迟到调度。

审批权限最有价值的取舍是“角色优先 + 白名单兜底”。JWT 增加 `role` claim 是为了让服务端不依赖配置拼身份，但旧 token 或内部客户端可能没有角色，所以保留 `approver-ids` 作为兼容路径。迁移体验上要提醒用户重新登录，新 token 才会带角色。

另一个值得记住的取舍是：当前测试用 mock 证明 RabbitMQ publisher/consumer 和 Outbox 服务，但真实 RabbitMQ 断链重连仍需要 Docker 基础设施上的故障演练。文档里不能把“接入了 RabbitMQ 代码”写成“已验证真实 MQ 传输”。

实现时最需要警惕的是把 Outbox 消费和业务更新当成一件事。正确的边界是：消费端先幂等检查，再执行副作用；重复事件直接返回成功，而不是再次执行业务。
