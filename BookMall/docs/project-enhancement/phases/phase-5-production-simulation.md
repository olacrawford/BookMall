# 阶段 5：把流程完整跑一遍并留下证据（第 6 天下午至第 7 天）

## 目标与业务价值

把系统变成可审查、可复盘、可面试的交付物，明确哪些能力接近生产验证、哪些只是本地模拟。

最终演示要体现“中台与业务分离”：AI 分析接口可以单独启动/停止，售后主流程在 AI 不可用时转人工；这比只展示一个页面更能证明架构设计。

## 前置条件

阶段 0-4 通过；前端或 curl 有固定演示脚本。

## 今天照着做

1. 从固定种子数据开始，按脚本依次执行自动退款、高金额审批、重复提交、Worker 恢复。
2. 每一步保存请求、响应、数据库状态和 `trace_id`，截图只补充不替代文字记录。
3. 清空浏览器缓存后再演示一次，确认页面展示的是持久化 Decision/证据而不是临时重算。
4. 执行 `mvn -f BookMall/pom.xml -q test`，将未通过项列入“已知问题”，不隐藏失败。
5. 最后才更新简历句子，并给每个句子附一个 `EV-*` 链接。

## 修改范围

售后列表/详情/审批页、Gateway 路由、演示数据、证据记录、README/面试资料；不新增未验证功能。

## 实施切片

1. 用户端提交和查询售后；详情页显示决策、证据、规则版本和流程状态。
2. 运营端显示待审批、批准/驳回、审计过滤；普通用户请求必须拒绝。
3. 执行自动退款、人工审批、重复提交、流程恢复四段演示。
4. 录制或保存 curl 输出/截图，所有关键结论绑定 `EV-*`。
5. 运行全量测试，整理已实现、已验证、模拟和未完成表。
6. 更新项目 README、系统设计、简历句子和 20 个追问答案。

## 交付产物

可重复演示脚本、截图/日志、全量测试结果、风险复盘、最终面试包。

## 验证方案

从空数据库或明确种子开始，按脚本顺序执行；第二次执行应因幂等而得到相同业务结果，不应新增退款副作用。

## 风险与回滚

演示失败时回退到 curl 和 Mock，不临时修改业务规则或数据库数据掩盖问题。

## 停止条件

证据缺失、测试未通过或状态标签混淆时，只交付计划和失败复盘，不声称生产就绪。

## 面试证据

至少完成自动路径、审批路径、重复请求和恢复路径各一份证据；每份说明限制。

## 必须沉淀

- `THOUGHT.md`：复盘一周哪些目标完成、哪些仅模拟、哪些应进入后续演进。
- `PIKE.md`：总结端到端闭环中最关键的一次失败和修复，不包装成线上事故。
- `CHANGELOG.md`：形成最终交付清单、演示脚本版本和已知问题。
- 面试卡片：项目介绍、核心架构图、自动/审批演示、可靠性故障和下一阶段集群演进各一张。
