# 阶段 3：测一次再决定要不要优化（第 5 天上午）

## 目标与业务价值

用小规模、可复现的测量确认瓶颈和成本，避免用平均耗时或想象中的并发包装项目。

本阶段至少完成一次并发实验（建议并发 5/10 两档），输出 P50/P95/P99、吞吐、错误率和资源占用；没有这些字段，不得在简历中写“高并发优化”。

## 前置条件

阶段 1-2 通过；准备固定 100 条订单和 20 条售后请求样本。

## 今天照着做

1. 先用同一脚本请求创建工单 20 次，记录响应时间，不先改缓存或索引。
2. 对工单列表、审批队列、审计查询执行 `EXPLAIN`，把扫描行数写进证据。
3. 只选一个最慢查询加索引，重新跑同一脚本，保留前后 P50/P95/P99。
4. 如果前后差异无法稳定复现，撤销优化并记录“停止条件已触发”。

## 修改范围

压测脚本、SQL 索引核对、Redis 幂等/短缓存、批量查询和 RabbitMQ 消费并发参数；不改变业务语义。

## 实施切片

1. 先测创建工单、查询详情、审批和重复退款的 P50/P95/P99、吞吐、错误率。
2. 用 `EXPLAIN` 检查工单状态/创建时间、审批状态/时间、审计 trace 索引。
3. 只针对有证据的慢点优化；每次优化后重复同一负载。
4. 记录资源占用和本地环境，区分 `verified` 与 `simulation`。

## 交付产物

压测脚本、前后对比表、索引变更和容量假设。

## 验证方案

结果必须包含环境、样本、并发、时间窗口和失败请求；没有压测工具时用 curl 脚本并明确局限。

## 风险与回滚

只在增量索引脚本中修改；发现锁竞争或缓存脏读立即回滚配置，不改变状态机。

## 停止条件

无法稳定复现实验或性能收益低于测量噪声时停止优化，保留基线。

## 面试证据

一张基线/优化对比表和一次 `EXPLAIN` 结果。

## 必须沉淀

- `THOUGHT.md`：记录负载模型为何这样定、哪些指标不能从本地样本外推。
- `PIKE.md`：说明一次优化前后的证据和没有继续优化的停止条件。
- `CHANGELOG.md`：列出索引、缓存或并发参数改动及回滚点。
- 面试卡片：P95/P99、缓存击穿、数据库索引和容量估算各准备一个可复现实验。
