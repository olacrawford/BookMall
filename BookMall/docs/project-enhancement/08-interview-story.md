# 面试叙事与证据边界

## 60 秒项目介绍（计划版）

“我把一套遗留电商交易骨架重构成 AI 售后智能运营平台。旧系统只提供订单、支付、库存和身份的迁移样本，最终业务按售后领域重新建模。用户投诉先进入工单，AI 识别诉求并通过白名单领域工具收集订单、物流和规则证据，再由 Policy 和风险等级决定自动退款、人工审批或风控介入。LLM 只输出结构化建议，资金和状态操作由可恢复工作流执行，退款用业务幂等键，关键动作写审计和 trace。第一周目标是用 Mock LLM/物流跑通自动退款和人工审批两条链路，并用故障测试证明重复请求和流程中断不会产生重复副作用。”

## STAR-L 亮点模板

### 亮点 1：AI 决策与业务执行隔离

- S：售后金额和状态不能由不可预测的模型直接修改。
- T：让 AI 提供可解释建议，同时保留确定性权限和一致性。
- A：定义 `Decision` 枚举/金额/证据/规则版本；Policy 校验；Workflow 执行。
- R：目标是非法 action 0 次进入执行；实际结果必须关联测试证据。
- L：真实模型仍可能误判，下一步做评测集和人工反馈闭环。

### 亮点 2：状态机、版本规则与审批

- S：高额或高风险售后不能自动赔付。
- T：同一工单在规则变化后仍可解释、可恢复。
- A：工单绑定 `policy_version`；显式迁移表；审批任务完成后恢复原 step。
- R：自动/审批/驳回三路单测和端到端记录。
- L：复杂退货状态暂不覆盖，后续按售后类型拆子状态机。

### 亮点 3：幂等、Outbox 与恢复

- S：退款、消息和 Worker 都可能重试。
- T：重试必须安全，流程必须能从检查点恢复。
- A：DB 唯一幂等键；业务事务写 Outbox；消费者状态幂等；Step 恢复扫描。
- R：重复请求副作用 1 次；中断后终态可达，具体数字以证据为准。
- L：第一周不承诺跨库强一致，明确最终一致和人工补偿入口。

## 追问分层

| 主题 | 原理问题 | 工程问题 | 取舍问题 |
|---|---|---|---|
| Agent/MCP | 为什么需要工具和契约？ | 超时、白名单、结果校验怎么做？ | 普通 HTTP 是否足够？为何不接 SDK？ |
| RAG | 为什么规则不能全靠模型记忆？ | 版本、权限过滤、召回失败怎么办？ | MySQL 关键词何时换向量？ |
| 工作流 | 状态机和工作流区别？ | checkpoint、抢占、重试上限？ | 为何不直接上引擎？ |
| 一致性 | Outbox 解决什么窗口？ | 重复消息、死信、补偿？ | 为何不用分布式事务？ |
| 安全 | AI 为什么不能退款？ | 用户/运营/审批如何隔离？ | 网关校验为何还要服务内校验？ |

## 真实性声明

当前仓库中售后/AI/MCP/RAG 尚未实现，面试只能说“设计目标”或“计划完成”。只有在 `evidence/` 中存在可重复命令、测试输出或截图后，才可把对应句子改为“已实现/已验证”。
