# 一周之后：可选增强清单

这份清单是第一周完成后的可选任务，不影响主链路。每项都先写出要解决的故障或慢点，再决定是否加组件；不能为了堆“分布式、集群、AI”名词而开工。

## 演进原则

1. 先用单体/单节点证明业务和一致性，再拆分部署单元。
2. 每次演进绑定一个故障场景、SLO 或容量问题，并保留前后对比证据。
3. 真实集群能力用本地多进程、Docker Compose 或测试环境模拟时，标记为 `simulation`；只有跨实例验证通过才标 `verified`。
4. 所有新增阶段继续执行 `THOUGHT.md + PIKE.md + CHANGELOG.md + EV-* + 面试卡片` 五件套。

## 接一个后续任务前先填这四行

```text
要解决的具体问题：例如停掉一个实例后请求失败
要改的文件/配置：例如 gateway 路由、after-sale application.yml、docker-compose
验证命令或操作：例如启动两个实例，停掉其中一个，再连续 curl 20 次
完成标准：例如成功请求 20/20，且能在日志中看到实例切换
```

如果这四行写不出来，说明还没有足够明确的问题，先不要加组件。

## 加餐 2：两个实例跑起来

### 目标

把逻辑域拆成可独立发布的 `after-sale`、`ai`、`mcp` 部署单元，证明请求能在两个实例间分发，实例异常时能摘除，调用超时不会拖垮工单。

### 实施切片

- 为每个服务定义版本化 REST/事件契约和健康检查。
- 在 Nacos 注册两个实例，Gateway 使用 Spring Cloud LoadBalancer；记录实例选择和请求 trace。
- Feign 配置连接/读取超时、有限重试和熔断；只对幂等查询重试。
- 通过 Docker Compose 停止一个实例，观察流量转移和错误率。

### 可以直接开工的任务

1. 复制 `bookmall-after-sale` 的启动配置为 `application-instance-2.yml`，只改端口和实例名。
2. 给 Gateway 增加售后路由，启动两个售后进程，连续执行 `curl /api/after-sales/health`。
3. 停掉实例 1，再执行 20 次查询；把成功数、响应实例和失败请求写入 `EV-*`。
4. 修改 Feign 超时为短值，注入一次慢响应，确认查询降级、退款写操作不重试。

### 不可省略的思考与面试材料

- 为什么售后写操作不能无脑重试？负载均衡解决不了什么问题？
- 客户端负载均衡与服务端负载均衡如何取舍？
- 注册中心不可用时，已有实例如何继续服务？
- 交付一张双实例拓扑、一段摘除故障日志和一张 P95 对比表。

## 加餐 3：消息与数据可靠性

围绕“退款已成功但通知失败”“消费者重复”“队列积压”建立可重放事件、死信处理、告警和人工补偿；不要直接宣称 exactly-once，解释实际采用的至少一次投递 + 幂等消费。

可以直接开工：给 Outbox Worker 增加失败重试开关；手动断开 RabbitMQ；恢复后观察事件重新发送；把重复消费前后的退款/订单行数做成对比表。

## 加餐 5：可观测性、发布与恢复

为每条工单建立跨 Gateway -> AI -> Tool -> Workflow -> Refund 的 Trace；实现灰度开关、数据库备份恢复、RTO/RPO 记录和回滚演练。任何“高可用”结论都必须附带实例数、故障注入、恢复时间和限制。

可以直接开工：先只接 Micrometer/Prometheus 一个指标；再用 Grafana 做待审批数和 Outbox 失败数两个面板；最后执行一次 `mysqldump` 恢复并记录耗时。

## 加餐 6：真实 AI 与 RAG 评测

Provider 采用接口切换，默认仍可 Mock。维护规则版本、Prompt 版本、模型版本、召回 chunk、Token、成本和人工反馈；用固定评测集比较关键词、向量和混合召回，不把单次回答当作准确率。

可以直接开工：先准备 20 条带“期望规则版本”的 JSON 用例；同一用例分别跑关键词和向量实现；输出命中/未命中清单，再决定是否保留向量库。

## 长期可选项

多租户、跨地域容灾、Kubernetes、服务网格、策略 DSL、复杂退货入库、实时风控模型和自动扩缩容都属于长期选项。只有当业务规模或故障实验提出明确需求时才立项，并补充成本、迁移和回滚方案。
