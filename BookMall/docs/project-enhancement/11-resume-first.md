## 先看结论：高含金量简历目标

下面 4 条是本周要倒推出来的投递版本。它们刻意避开“做了 CRUD、加了状态校验”这种低价值描述，改用架构边界、AI 工程化、分布式一致性和可测量结果来表达。`[实测值]` 在验收前不能替换成想象中的数字。

1. **AI 中台分层与独立治理**：基于 Spring Cloud Alibaba 将售后业务服务与 AI 能力中台分层，独立承载检索、Agent 编排和模型适配，业务侧只依赖标准分析契约；通过两个进程/实例的本地演练验证 AI 与业务链路可独立发布、故障隔离和资源隔离（`[实例数]`、`[失败转移结果]`，证据 `EV-011`）。
2. **规则知识库的混合检索工程化**：为售后规则构建关键词 + 语义检索的可切换检索层，加入分块、重排、版本绑定和权限过滤；用固定评测集记录召回命中、条款引用和上下文长度，解决纯关键词漏召回、纯向量丢术语和上下文冗余（证据 `EV-012`，没有 ES/Milvus 实测时只能写“设计并完成接口/本地模拟”）。
3. **多步骤 Agent 的受控工具编排**：采用主控编排器拆解意图识别、证据检索、业务工具查询和合规校验，工具注册表执行白名单、Schema、超时和重试；模型只生成结构化建议，写操作必须经过 Policy/Workflow，记录失败重试和人工接管（证据 `EV-013`）。
4. **分布式长链路的最终一致性**：针对 AI 异步调用、跨服务协同和消息重复，落地 Outbox、幂等消费、流程 checkpoint、Trace 和故障注入；在“退款成功但通知失败”“Worker 中断”“重复消息”场景中验证最终状态可恢复（证据 `EV-014`，结果写实际恢复时间和限制）。

## 简历成稿（完成并验证后使用）

### 项目名称

**电商售后智能运营平台**

### 项目概述

将一套遗留交易系统重构为面向订单异常的售后工单平台。平台把用户投诉转成工单，由 AI 识别诉求、调用只读领域工具收集订单/物流证据、检索售后规则，再由确定性策略决定自动处理、人工审批或风控介入；退款等资金动作由可恢复工作流执行，具备幂等、审计和失败恢复能力。

### 技术栈

Java 17、Spring Boot、Spring Cloud Alibaba、Gateway、Nacos、OpenFeign、MySQL、Redis、RabbitMQ、Vue 3；AI 部分使用结构化输出、领域工具、规则检索和可替换模型接口。

不要把四条都写成“熟悉/掌握”。每条必须能指向一个测试或演练，数字只写实际测量值。状态机、审批和 CRUD 是支撑这些亮点的实现细节，不单独占用简历主 bullet。

## 面试官追问时的固定顺序

1. 先说业务问题：售后金额、规则和权限不能由聊天模型直接决定。
2. 再说系统分工：AI 理解/检索/建议，售后域校验/编排，交易域执行。
3. 再说一个失败场景：模型输出非法、退款超时、消息重复或 Worker 宕机。
4. 最后说证据：给出测试命令、状态变化、日志字段和限制，不报未经测量的提升比例。

## 目前不能写进简历的句子

- “已实现真实大模型生产化”“支持百万并发”“完成集群高可用”：除非有环境、脚本、指标和故障演练。
- “实现 MCP Server/RAG”：必须说明工具边界、规则版本、召回证据和评测方式。
- “保证 exactly-once”：本项目默认是至少一次投递 + 幂等消费，应如实表述。
