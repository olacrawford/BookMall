# AI 售后智能运营平台阶段实施方案

## 实施基调

本方案按已有 `incremental-branch-training` 工作流组织，采用“AI 编码 + 核心手写”混合模式：

- AI 代写：工程骨架、配置、Controller/Mapper/CRUD、前端页面、测试骨架、文档初稿
- 手写核心：领域状态机、规则判定、工作流检查点、幂等、审计边界、MCP 工具契约、系统设计表达

每个阶段固定产出：

- 源码或 SQL
- `CHANGELOG.md`
- `THOUGHT.md`
- **PIKE 文档**：记录 Problem / Insight / Key Decisions / Evidence
- 验收记录

## PIKE 文档说明

PIKE 是本方案每个阶段的核心产出文档：

| 字母 | 含义 | 必须写清 |
| --- | --- | --- |
| P | Problem | 本阶段解决什么业务/工程问题 |
| I | Insight | 痛点和难点背后的工程判断、为什么这么理解 |
| K | Key Decisions | 关键取舍、替代方案、确定方案 |
| E | Evidence | 可运行验证、测试结果、产出物、面试可讲点 |

模板见 [PIKE模板.md](./PIKE模板.md)。每个阶段开始前先写 P/I，完成后补 K/E，交付物放在 `docs/stages/stage-{序号}-{名称}/PIKE.md`。

## 阶段总览

| 阶段 | 名称 | 建议天数 | 核心目标 | 主要分支 |
| --- | --- | --- | --- | --- |
| Stage 01 | 售后领域建模 | 0.5-1 | 工单/规则/状态机/流程边界定稿 | `stage/01-after-sale-model` |
| Stage 02 | 售后业务域 | 1.5-2 | 表/实体/策略/审批/工作流核心可运行 | `stage/02-after-sale-core` |
| Stage 03 | AI 决策域 | 1-1.5 | LLM 适配、Intent、MCP 工具、RAG 规则召回 | `stage/03-ai-decision` |
| Stage 04 | 端到端闭环 | 1-1.5 | 投诉到退款/审批/审计的前后端闭环 | `stage/04-end-to-end` |
| Stage 05 | 可靠性与验收 | 0.5-1 | 幂等、Outbox、恢复、测试、简历点收敛 | `stage/05-reliability` |
| Stage 06 | 运营端增强 | 1-2 周 | 工作台、审批看板、审计、可观测性 | `stage/06-operations` |
| Stage 07 | AI/RAG 增强 | 1-2 周 | 真实 LLM、向量库、RAG 评测 | `stage/07-rag-eval` |
| Stage 08 | 面试交付 | 1 周 | 系统设计、问答手册、模拟面试 | `stage/08-deliver` |

Stage 01-05 形成第一周闭环，Stage 06-08 是后续一个月增强。

## Stage 01 售后领域建模

目标：先定领域边界，不写业务代码。

输出物：
- 领域实体清单和字段草案
- 售后单状态机矩阵
- 规则版本模型
- 流程节点清单
- 第一版 PIKE 文档
- `THOUGHT.md` 字段设计思考

痛点与难点：
- 售后单和客服工单容易混成一个实体
- 退款、补偿、重发、退货需要不同状态流转
- 规则版本必须绑定工单，而不是查询当前规则
- 审批策略涉及金额、风险、商品类目多个维度

我们的思考：
- 用 `after_sale_order` 表达业务结果，用 `ticket` 表达沟通/处理过程
- 状态迁移必须显式定义，不使用多个布尔字段拼状态
- 金额统一 `DECIMAL`，业务内容使用枚举和版本号
- 第一周只保留一个最小状态机：`CREATED -> UNDER_REVIEW -> APPROVAL -> PROCESSING -> COMPLETED`，再加 `REJECTED / CANCELED / AUTO_HANDLED`

S级手写点：
- 字段建模与状态迁移矩阵
- 规则版本与工单绑定方式

AI 代写点：
- 文档模板、字段清单初稿、ER 图 Markdown

验收：
- [ ] 字段可解释
- [ ] 状态矩阵覆盖正常、驳回、取消、自动处理
- [ ] PIKE 文档已记录取舍

## Stage 02 售后业务域

目标：让售后域作为可运行后端服务存在。

输出物：
- `bookmall-after-sale` 模块
- `006_after_sale_ai.sql`
- 策略、审批、工作流、审计核心服务
- 单元测试
- CHANGELOG / THOUGHT / PIKE

痛点与难点：
- 工作流实例持久化，避免重启后丢失
- 审批任务和流程步骤如何关联
- 退款动作不能重复执行
- 售后结果如何与订单、支付、库存最终一致

我们的思考：
- 第一周先做“DB 驱动工作流”，每个 step 落库，任务调度扫描恢复
- 退款记录使用唯一业务幂等键；退款成功事件通过 MQ 通知订单
- 审计日志只记录关键业务动作：创建、AI 建议、规则命中、审批、执行、失败

S级手写点：
- 售后状态机流转函数
- 策略引擎判定（自动/审批/风控）
- 工作流步骤推进与恢复逻辑
- 退款幂等判断

AI 代写点：
- 模块骨架、Mapper、Controller、DTO、默认测试骨架
- 数据库脚本初稿

验收：
- [ ] 后端可启动
- [ ] 状态机拒绝非法迁移
- [ ] 退款重复请求只执行一次
- [ ] 关键动作写入审计

## Stage 03 AI 决策域

目标：AI 能根据工单上下文输出结构化决策，并收集证据。

输出物：
- `bookmall-ai` 模块
- `bookmall-mcp` 模块或同进程工具层
- Intent / Tool Result / Decision JSON Schema
- Mock LLM 与 Provider 适配器
- 规则文档分块和关键词召回
- CHANGELOG / THOUGHT / PIKE

痛点与难点：
- LLM 输出不稳定，可能返回非法 JSON 或不存在动作
- Agent 调用工具可能超时、失败、幻觉
- 工具必须受控，不能绕过业务规则
- RAG 需要同时给出规则出处，不能只凭模型记忆

我们的思考：
- AI 输入用 `TicketContext` 固定字段，输出用 `Decision` 固定 Schema
- 第一周工具层“先定义契约、后接真实 MCP”，内部可先用 HTTP 调用
- RAG 第一周用 MySQL 分块 + 关键词/规则标签召回，避免环境依赖
- 所有工具调用记录 `tool_name`、入参、结果、耗时、trace_id

S级手写点：
- Decision Schema 设计
- 工具调用边界与错误处理
- RAG 召回结果加工为证据列表

AI 代写点：
- LLM Client 骨架、MCP 接口骨架、分块脚本、Mock 数据
- 前端 AI 分析视图初稿

验收：
- [ ] 同一工单在 Mock LLM 下可稳定产出 Decision
- [ ] 工具调用失败不导致工单崩溃
- [ ] 输出包含证据 ID 和规则版本

## Stage 04 端到端闭环

目标：完成“用户投诉 -> AI -> 策略 -> 审批/自动处理 -> 退款 -> 审计”的完整链路。

输出物：
- 前端售后入口、工单详情、审批页
- 端到端演示脚本
- 手工验收用例
- CHANGELOG / THOUGHT / PIKE

痛点与难点：
- AI 分析、流程推进、退款、状态更新协调复杂
- 审批通过后要让流程继续而不是另写一套逻辑
- 页面需要展示 AI 判断依据，否则项目又回到“黑盒 Demo”
- 同一用户不能重复创建重复售后

我们的思考：
- 用 `ticket_id + after_sale_order_id + action + amount` 做幂等键
- AI 分析完成后把决策、证据、规则、风险持久化到工单中
- 前端只展示持久化结果，不依赖 AI 二次计算
- 退款成功后通过事件更新订单售后状态，流程步骤继续完成

S级手写点：
- 端到端主流程编排代码
- AI 分析结果落库
- 审批推动工作流恢复

AI 代写点：
- 页面、路由、请求封装、演示数据
- 集成测试脚本初稿

验收：
- [ ] 浏览器可跑通自动退款路径
- [ ] 浏览器可跑通人工审批路径
- [ ] 重复提交不产生重复退款
- [ ] 审计可查到完整链路

## Stage 05 可靠性与验收

目标：收敛第一周可交付状态，把稳定性问题显式处理。

输出物：
- 超时、重试、恢复、幂等测试
- Outbox 或最小事件一致性方案
- 第一周 README / 简历点 / 演示视频脚本
- CHANGELOG / THOUGHT / PIKE

痛点与难点：
- 退款成功但消息丢失
- 流程执行一半服务重启
- 消息重复消费
- 并发审批和自动处理竞争

我们的思考：
- 第一周使用事务内写业务记录 + 事务后发消息，再加消费端幂等
- 工作流节点落库并提供 `retry_count`、`status`、`next_schedule_time`
- 对退款、改订单状态、审计使用显式幂等判断
- 不追求完整 Outbox 方案，但保留 `outbox` 表作为后续增强点

S级手写点：
- 幂等判断代码
- 工作流恢复扫描
- 并发边界测试

AI 代写点：
- 测试用例批量生成、日志配置、演示脚本
- 架构图与 README 修订

验收：
- [ ] 模拟消息重复消费不产生重复退款
- [ ] 强制中断流程后可恢复
- [ ] 一周简历点和演示可讲通

## Stage 06 运营端增强

目标：从“能跑通”升级为“能用”。

输出物：
- 工单队列、审批看板、审计报表
- 用户与运营角色权限
- 日志、Trace、指标初步接入
- CHANGELOG / THOUGHT / PIKE

痛点与难点：
- 运营人员需要快速定位待处理任务
- 权限要区分用户、客服、审批人、风控
- 日志需要和工单、AI 调用、审批动作关联

我们的思考：
- 优先实现查询索引和状态筛选，不先做复杂仪表盘
- 继续复用网关 JWT + `X-User-Id`，运营角色单独用 `role` 字段控制
- Trace 先统一 `request-id` / `trace_id` 注入，后续接 OpenTelemetry

S级手写点：
- 运营权限边界
- 审计查询范围

AI 代写点：
- 工作台页面、状态统计接口、日志字段
- 基础指标采集

## Stage 07 AI/RAG 增强

目标：让 AI 层更接近真实企业能力。

输出物：
- 真实 LLM Provider 接入
- 向量库接入
- RAG 评测集和评估报告
- 成本/Token/耗时记录
- CHANGELOG / THOUGHT / PIKE

痛点与难点：
- 真实 LLM 输出和 Mock 不一致
- RAG 召回质量难以判断
- 不同售后场景需要不同检索策略
- Token 成本和响应延迟需要评估

我们的思考：
- 在 `LlmClient` 接口后增加 provider，保留 Mock
- 用 20-30 个种子问题组成 RAG 评测集
- 先衡量“规则命中率、证据可溯源、答案是否引用正确版本”
- 延迟和成本先记录，不盲目优化

S级手写点：
- 评测用例
- RAG 召回策略

AI 代写点：
- 向量库脚本、Provider 接入、评测工具
- 成本统计前端

## Stage 08 面试交付

目标：把项目变成能面试的项目。

输出物：
- 最终 README
- 系统设计文档
- 岗位定向面试问答手册
- 模拟面试记录
- 最终 CHANGELOG / THOUGHT / PIKE

痛点与难点：
- 能运行不等于能讲清
- 面试官会连续追问边界、失败、取舍
- 手写内容如果说不清，容易被识别为纯 AI 生成项目

我们的思考：
- 最终文档按“业务背景 -> 领域模型 -> 架构 -> 核心流程 -> 失败场景 -> 优化路径”组织
- 每人必须能独立画出状态机、退款链路、工作流恢复链路
- 模拟面试按“项目介绍、技术深挖、故障推演、方案对比”四轮执行

S级手写点：
- 系统设计文档
- 面试问答手册
- 核心代码随时可重写

AI 代写点：
- 文档润色、图表初稿、简历措辞
- 模拟面试追问与评分记录

## 第一周验收标准

- [ ] 后端编译通过，核心服务可启动
- [ ] 前端跑通用户提交售后
- [ ] AI 输出结构化决策并落库
- [ ] 自动退款路径可执行
- [ ] 人工审批路径可执行
- [ ] 重复请求不重复退款
- [ ] 关键动作有审计
- [ ] 3-4 个简历点已写实
- [ ] 每个阶段 PIKE 文档已更新
- [ ] S级手写点已由学习者独立完成

## 执行建议

1. 先进入 `stage/01-after-sale-model`，不要直接写代码。
2. 每阶段先写 PIKE 的 P/I，再设计，再编码。
3. AI 负责脚手架与重复工作，S级内容必须由学习者手写。
4. 一阶段一验收，验收不通过不进入下一阶段。
5. 一周目标以 Stage 05 为最低闭环，阶段 06-08 作为一个月增强。
